# Sessione 2026-08-07-01 — LOGDISC-1 + fix test date + purge naming Guidewire

## Contesto di partenza

Bug segnalato in produzione: con contesto su prod/nodo 3, la query «ultime 50
righe del access.log» rispondeva «non trovato», suggerendo `cc.log` al suo
posto. Stesso esito con il glob esplicito `"*undertow_access*.log"`. Causa:
`tail_named_log`/`grep_named_log` in `lib/dispatch.sh` passavano **solo**
`GUIDEWIRE_LOG_DIR` a `resolve_named_log_path()`/`open_glob_logs()`, mentre
`undertow_access_log.log` vive in `ACCESS_LOG_DIR`, una directory sorella sotto
lo stesso nodo — mai interrogata da quei due tool.

## Lavoro svolto

### 1. Decisione architetturale

L'utente ha stabilito che il "contratto" del profilo si ferma alla directory
del nodo (`LOG_SEARCH_ROOT`): sotto quella directory la struttura è **ignota**
e va **scoperta** ricorsivamente, non enumerata via directory note come
`APP_SUBPATH`/`GUIDEWIRE_SUBPATH`. Motivazione esplicita: un prossimo profilo
può non avere Guidewire, o organizzare i log diversamente dal nodo in giù —
i tool non devono richiedere tweaking continuo per ogni nuova forma.

Due decisioni di disambiguazione (via `AskUserQuestion`):
- **Cross-app miss**: se il log esiste solo sotto un'altra app, mai apertura
  silenziosa — si dice "non trovato" e si suggerisce l'app dove si trova.
- **Tie-break**: app di sessione corrente (`ACTIVE_APP`) prima, poi path più
  corto.

### 2. Implementazione (8 task, tutti completati)

| # | Modifica |
|---|----------|
| 1 | `resolve_log_glob()` (`lib/utils-logfiles.sh`) diventa ricorsivo: rimosso `-maxdepth 1`, aggiunto `\( -type f -o -type l \)` per escludere directory-trappola come `archive.log/`. Tie-break: app sessione → file non ruotato → path più corto → alfabetico. |
| 2 | `resolve_named_log_path()` (`dispatch.sh`) sostituisce 3 catene `find -maxdepth 1` duplicate con 3 chiamate in cascata a `resolve_log_glob`, centralizzando la policy di disambiguazione in un solo punto. |
| 3 | `open_glob_logs()` raggruppa le rotazioni dalla `dirname` del file scelto (flat), non dalla root — **ricorsione per la scoperta, flat per le rotazioni**. |
| 4 | `resolve-logs.sh` esporta `LOG_SEARCH_ROOT` (= `NODE_DIR`). |
| 5 | Rami `tail_named_log`/`grep_named_log` in `dispatch.sh` usano `search_root` unificato. Nessun cross-app silenzioso: `skip_named_log_not_found()` suggerisce l'app corretta. |
| 6 | `_log_names_in_dir()` diventa ricorsiva e non filtrante; il filtro dei basename di sistema si sposta a valle in `list_available_logs()` tramite il nuovo helper condiviso `_is_system_log_base()` (usato anche in `param-extract.sh`, eliminando una duplicazione preesistente). |
| 7 | Nuovo `tests/test-log-discovery.sh`, 17 asserzioni su fixture che replica il nodo reale (due app, omonimi cross-app, trappola `archive.log/`, directory profonda senza Guidewire). |
| 8 | Fixture di `test-dispatch-perf.sh` isolate per sezione (`sec1`/`sec2`/`sec3/gw`/`sec4/App/Sub/Deep`) — la ricorsione avrebbe causato leakage tra sezioni condivise; aggiunta 1 asserzione di ricerca multi-livello. |

## Valutazione richiesta: estendere la ricorsione a `search_all_logs.sh`?

Non ancora deciso, documentato in BACKLOG.md come LOGDISC-2 con motivazione.
Il tradeoff: estendere la ricorsione a `search_all_logs.sh` è coerente con il
principio 6 appena stabilito, ma cambia la natura dell'operazione — oggi
scansiona 4 directory *note*, con la ricorsione scansionerebbe *tutto* il
nodo, incluse eventuali directory con volumi molto maggiori (backup, archivi,
log di altre app mai considerate). Il costo del pre-gate letterale già
misurato per questo tool (righe 160-177 del file) dipende dal numero e
dimensione dei file aperti — più file scansionati, più tempo, anche con gate
attivo. Raccomandazione: non estendere ora senza una misura sul nodo reale
(quanti file/byte in più rientrerebbero nello scope); trattarlo come
esperimento a parte con soglia di tempo verificata, non come implementazione
diretta.

## Fase 2 — fix dei 6 FAIL pre-esistenti (date hardcoded)

I 2 FAIL aggregati (6 asserzioni) in `test-theme.sh` e `test-srch-named-log.sh`,
lasciati "da investigare" a fine Fase 1, sono stati diagnosticati e risolti
nella stessa sessione. **Causa**: le fixture di entrambi i file scrivevano
timestamp letterali (`"2026-08-06 10:00:00,000 ERROR..."`,
`[06/Aug/2026:10:00:00 ...]`), ma le query di test filtrano senza range
esplicito — cioè sulla data **corrente**. Il 2026-08-06 la fixture coincideva
con "oggi" e i test passavano per caso; il 2026-08-07 no. **Fix**: entrambi i
file ora generano la fixture con `_today_plain="$(date +%Y-%m-%d)"` e
`_today_apache="$(date +%d/%b/%Y)"` invece di stringhe letterali, oltre a un
fix analogo in `param-extract.sh` (estratto l'helper condiviso
`_is_system_log_base()` usato anche da `dispatch.sh`, eliminando una
duplicazione preesistente). Verificato: **84 PASS, 0 FAIL** — non era un bug
di codice introdotto tra sessioni, ma una fixture fragile rispetto al tempo
che passa.

## Fase 3 — purge del naming "Guidewire" dal contratto generico

L'utente ha segnalato variabili di contratto (`GUIDEWIRE_SUBPATH`,
`GUIDEWIRE_LOG_DIR`) ancora nominate sul middleware specifico, in
contraddizione con il principio di generalizzazione appena stabilito in
LOGDISC-1: "dove c'è Guidewire si parla di applicazione". Rinominate a
`CUSTOM_LOG_SUBPATH`/`CUSTOM_LOG_DIR` (opzione raccomandata su tre proposte),
poi propagato sistematicamente in 8 task:

| # | Ambito |
|---|--------|
| 1 | Codice prodotto: `system.conf`, `resolve-logs.sh`, `dispatch.sh`, `search_all_logs.sh` — rinomina delle variabili di contratto |
| 2 | Commenti tecnici: `utils-logfiles.sh`, `normalize-query.sh`, `tail_named_log.awk`, `grep_named_log.awk`, `tail_log.awk` |
| 3 | Profili: `domain.conf`/`examples.sh`/`entities.conf`/`unigrams.txt`/`bigrams.txt` di `liquido` e `usnext` |
| 4 | Documentazione utente: `README.md`, `docs/user/04-tools-and-modules.md` |
| 5 | Test: `test-log-discovery.sh`, `test-search-all-logs.sh`, `test-dispatch-perf.sh` (variabili esportate + commenti + fixture) |
| 6 | `CLAUDE.md`: principio 6 aggiornato + **nuovo principio 7** ("naming generico nel contratto, concreto solo nella prosa") |
| 7 | Regressione dopo ogni blocco: 84 PASS/0 FAIL confermato ripetutamente |
| 8 | Refusi residui in `entities.conf:30` e `BACKLOG.md:11` (commenti che descrivevano il contratto attuale con il nome vecchio) |

**Criterio di classificazione applicato** (ora principio 7 di CLAUDE.md): le
variabili/funzioni/categorie di *contratto* vanno sempre generalizzate; i
commenti che descrivono il *meccanismo generico* mantengono "Guidewire" solo
come esempio parentetico; la prosa che descrive un *fatto concreto* del
profilo `liquido` (formato di log realmente osservato, sinonimi digitati dagli
utenti, bug storici in session log/BACKLOG.md) resta inalterata perché è dato
di dominio, non leak di contratto. Lasciati intenzionalmente: `README.md`,
`docs/user/01-overview.md`, `docs/user/04-tools-and-modules.md:116` ("31 log
Guidewire" — dato reale), `BACKLOG.md` (prosa storica sul bug LOGDISC-1/2),
`entities.conf` (alias/`APP_CANONICAL` — sinonimi reali digitati dagli utenti).

**Verifica finale**: `bash tests/run-tests.sh` → **84 PASS, 0 FAIL**. Nessuna
regressione introdotta dal purge.
