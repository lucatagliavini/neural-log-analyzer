# Sessione 2026-08-05-03

## Lavoro svolto

Bug fix in `search_all_logs`, trovato durante la validazione manuale in produzione
dell'utente (query: `cerca "searchHub" nel nodo 4 di produzione nelle ultime 2 ore`).

### Diagnosi

Sintomo riportato: per il file `policysearch.log` la tabella mostrava `MATCH=46` ma
PRIMO/ULTIMO MATCH vuoti (`-`). Ipotesi iniziale dell'utente: un formato di timestamp non
riconosciuto dal convertitore. **Causa reale, diversa**: il filtro temporale (introdotto
nella sessione precedente, commit `adb8f7b`) girava in bash solo sulle righe già estratte
da `grep -iE`, perdendo il contesto del file.

In `policysearch.log` (Guidewire) il pattern `searchHub` (case-insensitive) matcha anche le
righe di stack trace multi-riga tipo `at it.unipol.sx.bo.SearchHubExtApi...` — "SearchHubExtApi"
contiene "searchHub" come sottostringa. Queste righe non hanno un timestamp proprio (sono
continuazioni dell'eccezione sopra) e venivano **sempre mantenute** dal filtro, anche quando
l'eccezione a cui appartenevano (con il suo vero timestamp) era fuori dalla finestra
richiesta. Risultato: righe "match" orfane senza data associata.

Riprodotto dal vivo via SSH su `lxprworkerliq01` con la query esatta dell'utente, poi isolato
con un prototipo `gawk` standalone prima di toccare il codice.

### Fix

Sostituita la pipeline `grep -iE` + filtro bash riga-per-riga con un'unica passata `gawk`
(nuovo file `lib/tools/search_all_logs.awk`) sull'**intero file**, non solo sulle righe che
matchano. La funzione traccia un "timestamp effettivo" per ogni riga: quello proprio, o —
se assente — quello dell'ultima riga con timestamp vista scandendo in ordine. Questo è
determinabile solo scansionando il file per intero: è la stessa informazione che
`filter_errors.awk` ricostruisce con `is_stack_frame()`, qui reimplementata perché
`search_all_logs.sh` non aveva mai avuto una fase AWK.

`search_all_logs.sh` ora invoca `gawk -f search_all_logs.awk` per ciascun file (via
`gunzip -c | gawk ...` per i `.gz`), passando `pat`/`tf`/`tt`; il worker riceve
`"hits|first_ts|last_ts"` invece di dover post-processare l'output di `grep`. Rimossi
`_sal_line_ts()` e `_SAL_MONTHS` da `search_all_logs.sh` (logica timestamp ora solo nel
file awk).

## ⚠ Problema aperto, priorità sessione successiva — PERF-SAL

L'utente ha segnalato, subito dopo la verifica live, che **il tool sembra molto più lento
di prima**. Non ancora misurato: la sessione si è interrotta prima di poter confrontare i
tempi `grep -iE` (vecchio) vs `gawk -f search_all_logs.awk` (nuovo) sui file reali.

**Ipotesi principale, da verificare per prima**: `gawk -f search_all_logs.awk` ora scandisce
**ogni riga di ogni file** per estrarre/ereditare il timestamp (necessario per il fix), mentre
prima `grep -iE` si limitava a estrarre le righe matchate e il filtro bash operava solo su
quelle poche righe. Su file da 150-200k righe (misurato in sessione precedente:
`policysearch.log` ~197k righe, `performance_integrations.log` probabilmente comparabile,
vista la cardinalità dei match) il costo è passato da "grep sull'intero file + poche righe in
bash" a "gawk sull'intero file con una regex di match timestamp per riga, sempre eseguita,
anche quando il filtro temporale non è richiesto" — il costo per-riga è più alto anche nel
caso "nessun filtro" (`tf`/`tt` vuoti), perché la ricerca del timestamp con `match()` gira
comunque per determinare `eff_ts` da riportare in tabella.

Percorsi di indagine per la prossima sessione, in ordine:
1. Misurare concretamente i tempi `time gawk -f search_all_logs.awk` vs `time grep -iE` sugli
   stessi file reali (comando preparato ma non eseguito: rifiutato dall'utente per "niente
   altro sviluppo oggi" — riprendere da qui).
2. Se confermato che il costo è nella scansione riga-per-riga del timestamp: valutare se
   l'estrazione timestamp si può saltare quando `tf`/`tt` sono entrambi vuoti E non serve
   comunque il first/last (non è il caso: first/last servono sempre per la tabella) — quindi
   il costo del **filtro temporale** e quello della **tabella first/last** sono ora accoppiati
   nello stesso attraversamento, dove prima erano disaccoppiati (grep veloce sempre, filtro
   bash lento solo se richiesto, first/last calcolato solo sulle righe già ridotte).
3. Ottimizzazione più mirata: fare il match del pattern (`$0 ~ pat`) **prima** di tentare
   l'estrazione del timestamp con `match()` — oggi il codice fa il contrario (calcola sempre
   `ts`/`eff_ts` per ogni riga del file, poi controlla se la riga matcha il pattern). Invertire
   l'ordine risparmierebbe il costo di `match()` per le righe che non contengono il pattern
   (la maggioranza), MA romperebbe l'eredità del timestamp per le righe successive che non
   matchano il pattern ma che servirebbero comunque a "aggiornare" `last_seen_ts` per la riga
   matchata successiva — quindi il timestamp deve essere sempre calcolato per OGNI riga,
   indipendentemente dal match. Il possibile guadagno è quindi limitato: probabilmente serve
   ottimizzare la regex del timestamp stesso (oggi due `match()` con regex letterali per
   riga, invece di IGNORECASE + branch ottimizzato), o valutare se gawk possa essere più
   lento di grep per motivi strutturali (regex engine, overhead di IGNORECASE=1 applicato
   anche al pattern del timestamp che non ne ha bisogno).
4. Considerare se il confronto corretto non sia "prima" vs "dopo" ma piuttosto "prima" (grep
   veloce + niente first/last quando MATCH=0, filtro bash lento SOLO sui pochi risultati) vs
   "dopo" (gawk che scandisce sempre l'intero file, anche per i 30+ file "senza match" della
   tabella — nel test odierno 30 file su 33 erano "senza match": questi ora vengono comunque
   scansionati per intero da gawk invece di un grep rapido che si ferma presto se non trova
   nulla). Se questo è il caso, la fascia di file "senza match" è quella che ha perso più
   velocità in proporzione.

Nessuna modifica di codice fatta per questo problema in questa sessione — solo diagnosi
preliminare scritta qui per non perdere il contesto. **Da riprendere come primo punto della
prossima sessione**, come richiesto esplicitamente dall'utente.
