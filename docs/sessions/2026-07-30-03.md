## Lavoro svolto

### Fix classificazione filter_errors (CHIUSO)

**Problema**: query come "quali sono gli errori in produzione sul nodo 5" venivano
classificate come `grep_named_log` (66%) invece di `filter_errors`. Il dispatch
faceva poi SKIP perché `NAMED_LOG` era vuoto.

**Causa**: tutti i 68 esempi di `filter_errors` nel dataset contenevano esplicitamente
"server log" o "log applicativo". Query generiche senza nome del log cadevano nella
zona di `grep_named_log` (93 esempi, classe più rappresentata).

**Fix**: aggiunti 13 esempi `filter_errors` senza riferimento al log:
- "ci sono errori in produzione"
- "quali sono gli errori in produzione sul nodo 5"
- "errori sul nodo 3 di produzione"
- "cosa non va in produzione"
- "anomalie rilevate in produzione"
- e altri 8 analoghi

### build_dataset.py — backend Python (CHIUSO)

**Problema**: `build-dataset.sh` impiegava ~3 minuti per 968 esempi (2 subprocess
fork per riga: normalize-query.sh + query-to-features.sh).

**Soluzione**: `lib/build_dataset.py` — replica in-process di tutta la logica:
- Carica vocabolario (unigrams.txt / bigrams.txt) una volta
- Replica `normalize-query.sh`: normalizzazione APP/ENV/NODE con regex Python
- Replica `query-to-features.sh`: vettorizzazione con `re.search()` in loop
- Punto critico: `pattern="${pattern// /}"` in bash rimuove gli spazi dai pattern
  prima del match → replicato con `.replace(' ', '')` per output bit-identico
- Verificato: 968/968 vettori identici al bash (con NORM_QUERY esportata)
- Fallback automatico su bash se `.venv` assente

**Benchmark**: 90ms vs 172s → **1900× speedup**

`build-dataset.sh` aggiornato con lo stesso pattern di `train.sh`:
autodetect `.venv/bin/python3` → usa Python, altrimenti bash.
