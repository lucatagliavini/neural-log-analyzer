## Lavoro svolto

### 1. Correzione dei 4 bug nel test (non nel codice di produzione)

1. **Scoping bash**: `_load_profile()` era una funzione che sourciava `tools.conf`/
   `domain.conf` al suo interno — `source` in bash non apre un proprio scope, quindi
   ogni `declare -A` in quei file diventava locale alla funzione e spariva al `return`
   (`count_status: unbound variable`). Eliminata la funzione, caricamento inlineato due
   volte (un profilo alla volta). Verificato che non è un problema di produzione:
   `chatbot.sh` sorcia sempre a top-level.
2. **`SOURCE_LABEL[named]` mancante** in entrambi i `domain.conf` (gap reale
   nell'invariante di chiusura, non ancora sfruttato oggi ma richiesto dal test per non
   lasciare un buco silenzioso). Aggiunto in `profiles/liquido/domain.conf` e
   `profiles/usnext/domain.conf`.
3. **Bug AWK nel test**: l'estrazione della sezione-categoria per `service_times`
   confondeva l'header di categoria con la riga del tool stesso (stessa indentazione
   dopo lo strip dei colori). Corretto confrontando contro l'elenco esatto di
   `HELP_CATEGORIES` invece di indovinare dalla forma della riga.
4. **Test non agganciato**: `test-help-sources.sh` non era in `tests/run-tests.sh`.
   Aggiunto a `run_unit_tests()`.

### 3. Verifica dal vivo post-deploy: scoperto un bug reale di produzione

La query `chatbot.sh --profile profiles/liquido --env prod --query 'aiuto'` sul server
restituiva **output troncato ed exit code 1**: solo la categoria "Log HTTP (access log)"
veniva stampata per intero, le successive ("Server log JBoss", "GC / JVM", "Log
applicativi custom", "Ricerca cross-log", "Esplora log del nodo") mancavano del tutto.

Escluso un problema di buffering SSH (confermato con redirect a file). Tracciato con
`bash -x` (`/tmp/help_trace.out` sul server): il ciclo `for tool in TOOL_NAMES` risultava
interrotto subito dopo aver valutato `show_help`, senza mai raggiungere `search_all_logs`
e `list_logs`, e il controllo saltava direttamente a `_rotate_query_logs`.

**Causa**: `_rotate_query_logs` è registrata come `trap '_rotate_query_logs' EXIT` in
`chatbot.sh` (riga 322) — la sua esecuzione nel trace non indicava una prosecuzione
normale del flusso, ma un'**uscita immediata dello script**, con il trap che scattava
come cleanup. La radice era in `tool_help_category()` (`lib/dispatch.sh`): il ramo
`none) return ;;` usa un `return` senza valore esplicito, che in bash eredita l'exit
status dell'**ultimo comando eseguito** prima del `return` — qui il test
`[[ "$first" == *"|"* ]]`, falso per `"none"` (status 1). L'assegnazione
`tool_cat="$(tool_help_category "$tool")"` per `show_help` (l'unico tool con kind
`"none"`) propagava quello status 1 e, sotto `set -euo pipefail` (`chatbot.sh`, non il
test — che usa `set -uo pipefail` senza `-e` per necessità di scoping, vedi punto 1
sopra), faceva terminare l'intero script in quel punto.

**Perché non intercettato dal test**: `tests/test-help-sources.sh` non ha `-e` attivo, e
quindi non esercita mai questo scenario — un punto cieco strutturale del file, non solo
un'omissione.

**Fix**: `return 0` esplicito in `tool_help_category()`. Aggiunto un test di
regressione dedicato che isola lo scenario `-e` in un subshell separato
(`bash -c 'set -euo pipefail; ...'`), l'unico modo per verificarlo senza rompere lo
scoping degli array associativi sourciati nel resto del file di test. Confermato che il
test fallisce sul codice pre-fix e passa dopo (verificato con `git stash`).
