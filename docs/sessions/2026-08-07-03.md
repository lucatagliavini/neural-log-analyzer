# Sessione 2026-08-07-03 — LOGSEL-1: errori nell'access log, misrouting + falso positivo silenzioso

## Contesto di partenza

Bug segnalato in produzione: «errori nel access.log di produzione stamattina
del nodo 4» rispondeva con righe prese dal **server.log**, senza alcun
avviso. Diagnosi (in un segmento precedente, non ripetuta qui): due difetti
indipendenti, non un regresso di LOGDISC-1/3 (quel lavoro — scoperta file,
sinonimia `access` → `undertow_access_log` — funzionava correttamente).

- **D1 (misrouting)**: zero esempi nel dataset per la firma «errore + access
  log senza status code»; la rete instradava sull'unica firma nota
  (`filter_errors` su server log), strutturalmente identica a meno del nome
  del log.
- **D2 (falso positivo silenzioso, il più grave)**: il ramo `filter_errors`
  non emetteva alcun indizio del file letto — `print_log_source()` esisteva
  già (creato per `tail_log`) ma non era stato migrato ai tool di sistema.

Piano approvato dall'utente in `/home/uga04128/.claude/plans/fizzy-orbiting-hamster.md`,
con due decisioni esplicite: routing multi-label (`count_status,distribute_status`,
non una nuova classe) e trasparenza `print_log_source()` su **tutti** i tool
di sistema, non solo sul caso specifico. Vincolo esplicito: nessuna regola ad
hoc per tipo di log («errori = 4xx/5xx» cablato per l'access log avrebbe
violato la generalizzazione).

## Lavoro svolto

1. **`lib/dispatch.sh`** — `print_log_source()` aggiunta a tutti i rami di
   tool di sistema che prima ne erano privi: `count_status`,
   `distribute_status`, `slow_requests`, `traffic_volume`, `filter_errors`,
   `service_times`, `gc_stats`, `filter_ip`, `filter_app_errors`,
   `correlate_gc_slow` (due sorgenti — gc + access — passate in un'unica
   chiamata, l'helper gestisce già il caso multi-path). Chiude D2.
2. **`profiles/liquido/dataset/queries_labeled.txt`** — 16 esempi
   multi-label `count_status,distribute_status` per la firma mancante
   (errore/eccezione/anomalia + access log/log http/log delle richieste,
   senza status code esplicito). Nessun cambio a vocabolario/topologia
   (111→48→16 invariata) — solo dataset (1070→1086) e retrain. Chiude D1.
3. **`lib/tools/grep_named_log.awk`** — distinzione generica fra "formato
   non riconosciuto" e "nessuna riga col livello cercato": contatore
   `matched_format` separato da `count`; se ci sono righe lette ma nessuna
   nel formato timestamp+livello atteso, messaggio dedicato con conteggio
   righe e suggerimento di cercare una stringa specifica, invece del
   precedente (fuorviante) `Nessuna riga trovata (level=X)`. Nessuna
   conoscenza del tipo di log nel codice — vale per qualunque log con
   formato diverso, non solo per l'access log.
4. **Documentazione**: nuova voce **LOGSEL-1** in `BACKLOG.md` (3 sotto-voci
   a/b/c per i tre fix); corretto un riferimento obsoleto a `profiles/<nome>/vocab.sh`
   in `CLAUDE.md` (rimosso il 2026-07-29, contenuto ora in
   `unigrams.txt`/`bigrams.txt` + `domain.conf`). Non aggiunto un nono
   principio — il caso ricade sotto il principio 8 già esistente
   (centralizzare significa migrare tutti i chiamanti).

## Verifica

`bash tests/run-tests.sh --parity`: **87 PASS / 0 FAIL**, parità bash/Python
confermata su 1086 query (111 feature). Cinque confini adiacenti riverificati
senza regressione dopo il retrain (server.log via `filter_errors`, access.log
via `tail_log`, `cc.log` via `grep_named_log`): confidenza 0.96-0.9998,
invariata rispetto a prima del retrain.

Metriche di training: MSE 0.000980 (epoca 197), early stop epoca 297,
exact_match 0.9797, precision 0.9815, recall 0.9929, F1 0.9872.

**Lezione di metodo, autocorretta durante la verifica**: un primo tentativo
di verificare i confini chiamando `lib/infer.sh` direttamente su query
letterali (bypassando `normalize-query.sh`) produceva un falso allarme
(`errori nel cc.log` sembrava instradare su `filter_errors` invece di
`grep_named_log`). Risolto confermando via `git stash` che lo stesso
risultato esisteva già prima delle modifiche di questa sessione (nessuna
regressione), poi correggendo la metodologia: `infer.sh` va sempre chiamato
dopo aver sourcato l'output di `normalize-query.sh` ed esportato
`NORM_QUERY`, esattamente come fa `tests/run-tests.sh:229-235` e come fa
`chatbot.sh` in produzione. Nessun bug reale nel codice — l'errore era
interamente nel test ad hoc.
